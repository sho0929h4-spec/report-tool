## 1. 目的とスコープ

UIプロトタイプ（計画1・モックデータ）を、**作業担当者が現場で実際に使える本物のアプリ**にする。
管理者向け機能は「案件を登録して作業者に渡す」最小限のみ。詳細（原価・承認・設定）は後続スライス。

### 含むもの
- Supabase 新プロジェクト（認証・DB・RLS）
- ログイン画面（メール+パスワード）
- 「今日」ホーム・案件一覧・案件詳細を**ログイン中の作業者の担当案件のみ**で表示（admin は全件）
- 作業開始/終了の打刻（ステータス遷移 scheduled→in_progress→submitted）
- 報告フォーム: 区分4ボタンでフォーマット切替。漏水調査は詳細フォーマット（§4）
- 写真: 撮影チェックリスト誘導→端末内圧縮→Cloudflare R2 へ逐次アップロード
- 管理者の最小案件登録フォーム（§5）と、登録情報の作業者画面への自動引き継ぎ
- pg_cron 日次ジョブ（無料枠の7日停止対策。削除処理は当面空実装）

### 含まないもの（後続スライス）
- 原価タブ・請求額・単価設定の実データ化（スキーマだけ先行作成）
- 管理者の承認（confirmed 化）・差し戻しフロー
- 共有ページ（share.html）・連絡タブの実データ化
- 旧ツール IndexedDB 履歴のクラウド移行ボタン
- 旧管理ツール（Netlify / 旧 Supabase zalgyrgjwjdgvklqhdrg）からのデータ取り込み
- ネット公開（ホスティング方法は別途決定。GitHub への push は現在認証なしで不可）
- 保存期間の自動削除の本実装・設定画面

## 2. 画面フロー（承認済み）

```
ログイン（メール＋パスワード）
  ↓
「今日」ホーム … 自分の担当現場だけが時刻順に並ぶ
  ↓ タップ
案件詳細 … 一覧・詳細とも担当者フィルタ済み
  ↓
[作業開始] 大ボタン → 開始打刻＋ステータス「対応中」
  ↓
報告フォーム … 区分ボタンで切替
[漏水調査] [原状回復] [復旧工事] [設備等原因工事]
  ↓
[報告を送信] → 終了打刻＋「報告済み」
```

- 区分は管理者が案件登録時に設定。報告フォーム上でも変更可（現場で判明が変わるケース）
- admin ログイン時は従来どおり全件表示＋登録フォーム（FAB）

## 3. 区分と報告フォーマット

- `work_type` は4値: **漏水調査 / 原状回復 / 復旧工事 / 設備等原因工事**（DB には日本語のまま保存、CHECK 制約）
- 漏水調査 → §4 の詳細フォーマット
- 他3区分 → 共通シンプル版: 実施項目チップ＋作業実施内容（テキスト・音声）＋前後写真。区分ごとの詳細は後続で個別に詰める

## 4. 漏水調査フォーマット（承認済み・既存ツールを土台に改修）

| 要件 | 画面での形 |
|---|---|
| 写真撮影箇所の誘導 | 撮影チェックリスト: **作業前 全景（必須）・漏水箇所 近景（必須）**・調査測定状況・応急対応後。タップ→カメラ起動→自動チェック。必須未撮影は送信時に警告 |
| 調査内容 | 実施項目チップ（目視確認・耐圧テスト（給水管）・耐圧テスト（給湯管）・スコープカメラ調査・開口調査・排水テスト・給湯管更新・交換・給水管更新・交換・配管修繕・水栓交換・開口補修・復旧・防水工事＋その他）→タップで文章に自動反映＋自由入力・音声入力 |
| 原因箇所（場所） | 場所チップ（キッチン・浴室・洗面・トイレ・給湯器・天井裏・PS・不明 ほか）＋自由入力 |
| 原因と判断した理由 | テキスト＋音声入力（既存「原因」欄を「箇所」と「理由」に分割） |
| 水漏れは止まっているか | 大ボタン2択 [止まっている][止まっていない]。止まっていない場合のみ「理由」欄＋応急対応の選択（養生対応済み・すでに養生対応済み・入居者希望により養生せず・元栓を閉めた）を表示 |
| 今後必要な対応 | 提案チップ（再調査・開口補修の手配・配管修繕の手配・保険対応・見積作成・要相談 ほか）＋自由入力 |

`cases.report` (jsonb) のキー:

```json
{
  "format": "漏水調査",
  "survey_items": ["目視確認", "耐圧テスト（給水管）"],
  "survey_items_other": "",
  "survey_detail": "調査内容の本文",
  "cause_location_chips": ["キッチン"],
  "cause_location_free": "",
  "cause_reason": "原因と判断した理由",
  "leak_stopped": "止まっている | 止まっていない",
  "leak_not_stopped_reason": "",
  "emergency_action": "養生対応済み など（止まっていない時のみ）",
  "next_action_chips": ["再調査"],
  "next_action_free": ""
}
```

共通シンプル版は `{"format": 区分名, "survey_items": [...], "survey_detail": "..."}` のみ。

## 5. 案件情報の引き継ぎ（管理者 → 作業者）

- 管理者の最小登録フォーム: **物件名（必須）・号室・住所・対応日時・区分・担当者・現地対応指示**
- 登録した情報は作業者の「今日」ホーム・一覧・詳細・報告フォームに**自動で引き継がれ、作業者は再入力しない**
- 報告フォームの物件名・号室・住所・案件 No は案件から自動セット（編集可）

## 6. データモデル

親設計書 §5 の SQL を全テーブル採用（costs / worker_rates 含めスキーマは最初から作成。UI は後続）。差分:

- `cases.work_type` → `CHECK (work_type in ('漏水調査','原状回復','復旧工事','設備等原因工事'))`
- `photos.check_item text` を追加（撮影チェックリスト項目キー: `zenkei` / `kinkei` / `sokutei` / `after` / null）

RLS は親設計書 §6 のとおり（worker は担当案件のみ更新可、costs / worker_rates / invoice_amount は admin のみ）。

## 7. バックエンド構成

- **Supabase 新プロジェクト**を CLI で作成（org: bagituyehozynbtqryeo・東京リージョン）。既存 `zalgyrgjwjdgvklqhdrg` とは完全分離
- **CLI 作業ディレクトリは `app/backend/`**。repo 直下の既存 `supabase/` フォルダ・リンク・migrations には一切触れない
- 鍵類（DB パスワード・R2 認証情報）は `app/backend/.env` に保存し **gitignore に追加**（コミット禁止）
- 写真: Cloudflare R2 バケット1つ。Edge Function `sign-photo` が JWT 検証→担当確認→署名 URL（PUT/GET・期限10分）発行
- pg_cron 日次→`purge-expired`（当面は何もしない空実装。無料枠停止対策を兼ねる）
- フロントの接続先は `app/shared/config.js` に一元化（プロトタイプの Store 窓口を supabase-js 実装に差し替え。画面側の呼び出し口は変えない）

### 前提条件
- Supabase: CLI 認証済み（確認済み・ユーザー操作不要）
- Cloudflare: **wrangler のログイン期限切れ**。R2 構築タスクの開始時にユーザーが `wrangler login` を1回実行する

## 8. 認証・初期アカウント

- Supabase Auth メール+パスワード
- 初期メンバーは手動作成: admin 1名（ユーザー本人）+ worker（実運用の作業担当者。まずテスト用に1〜2名）
- セッションは supabase-js が端末に保持（毎回ログイン不要）

## 9. 写真アップロード

- 端末内で圧縮: 長辺 1600px / JPEG（約300KB）＋サムネ（約30KB）
- チェックリストタップ→カメラ起動→撮影即アップ（逐次）。失敗分はキューに残し再試行ボタン
- R2 キー: `{tenant_id}/{case_id}/{uuid}.jpg`（本体）/ `thumb/` （サムネ）

## 10. 動作確認方法

- Mac 上のローカルサーバー（port 8080 常駐中）＋スマホは同一 Wi-Fi で `http://<MacのLAN IP>:8080/app/` に接続
- 実機（iPhone/Android）でカメラ撮影→アップロードまで確認

## 11. テスト（スライス1）

- RLS: 2テナント・3ユーザーで越境アクセス全拒否の SQL テスト。worker が costs / worker_rates / invoice_amount を読めないこと
- 打刻: worker の scheduled→in_progress→submitted 遷移可・confirmed 不可
- 送信ガード: 必須撮影（全景・近景）未撮影時の警告、調査内容空での送信ブロック
- 報告保存: 漏水調査フォーマットの全キーが保存→admin で閲覧できること
- 写真: 圧縮後サイズ・アップ失敗→再試行（スマホ実機）
